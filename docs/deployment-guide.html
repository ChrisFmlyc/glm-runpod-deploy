01

What you're deploying

GLM-5.3-Flash is a hybrid mixture-of-experts model released 2026-08-26. It is not a conventional dense transformer, and three of its architectural quirks directly cause problems later in this guide — so they're worth knowing before you spend money.

PropertyValueWhy it matters here
Total parameters321,323,031,390Identical in base and abliterated builds — shapes are interchangeable
PrecisionFP8 e4m3 + BF16314.4B FP8, 6.9B BF16 (vision tower, embeddings, norms)
Weights on disk306 GiB62 safetensors shards; the single biggest constraint
Layers4534 KDA linear-attention + 11 sparse MLA, interleaved
Experts288 routed + 1 shared8 active per token
Attention heads64Tensor-parallel size must divide 64 — so 3, 5, 6, 7 GPUs are invalid
Attention typeNoPE MLAqk_rope_head_dim: 0, kv_lora_rank: 512 — needs FlashInfer ≥ 0.6.17
Max context1,048,576Theoretical; this guide uses 65,536 for a sane first boot
ModalityText + visionGLM-4.1V tower included in the checkpoint

The two builds

  • zai-org/GLM-5.3-Flash — the official base model. MIT licensed, not gated, no HF token needed.
  • dealignai/GLM-5.3-Flash-UNCENSORED-FP8 — an abliterated derivative with safety refusals removed. Same architecture, same parameter count, same 306 GiB.

Both are served by the identical procedure. Only the download URL and the --model path differ.

Deploy the base first

The abliterated build is a community derivative with no usage history. If you start there and it fails, you cannot tell whether the checkpoint or the (pre-release) inference engine is at fault. Standing up the base first costs one extra download and makes every later failure diagnosable. Both bugs in section 08 turned out to be engine bugs, not checkpoint bugs.

306 GiB of weights must fit in aggregate VRAM, with headroom for KV cache, Mamba state blocks and activations. Budget roughly 340–360 GiB total.

Hopper versus Blackwell

On Blackwell (B200) you may add --kv-cache-dtype fp8. On Hopper (H100/H200) that flag is unsupported for this model and will fail — leave it off and run BF16 KV. The model card's suggested launch command assumes a GB200 and will not work as written on Hopper.

Prefer four large GPUs over eight small ones

A free 8-GPU node is materially harder to schedule than a free 4-GPU node. During testing, 8-GPU requests failed every attempt across two datacenters while 4-GPU requests succeeded.

The datacenter trap

Your GPU and your storage must be in the same datacenter, and not every datacenter offers both. During testing, the only region with free 4 × H200 capacity (US-GA-2) did not support network volumes at all, and the region with volumes (EU-FR-1) intermittently had no GPUs. Check both before committing — see BUG-06.

03

Before you start

  • A RunPod account with credit. Budget $15–25 for a first deployment including mistakes.
  • A secret you invent now to protect the endpoint. Any random string, e.g. glm- followed by 32 random characters. Write it down; you'll need it three times.
  • No Hugging Face token is required — both repositories are public and ungated.
  • Roughly 45 minutes, most of it waiting.
Read this before clicking Deploy

A GPU pod bills from the moment it starts, whether or not the model is loaded, and whether or not it is crash-looping. At $18.36/hr an overnight mistake costs about $440. Set a billing alert, and jump to section 09 before you walk away.

04

Deploy the base model

The strategy is one pod, two images. You start the pod on a general-purpose PyTorch image that gives you a shell, download the weights to persistent storage, then edit the same pod to run vLLM. Doing it this way holds your scarce multi-GPU allocation for the whole process instead of releasing it and re-competing for capacity.

Console or CLI

The steps below use the web console. Section 10 gives the REST equivalent of every one of them — and those API calls are the ones that were actually executed to produce this deployment, whereas these console click-paths are transcribed from RunPod's published UI. If a label here does not match what you see, trust section 10.

01

Create storage

In the RunPod console go to Storage → Network Volumes → New Network Volume.

  • Size: 400 GB for one model, 750 GB to hold base and abliterated side by side
  • Datacenter: one that offers both network volumes and your chosen GPU

If the console refuses your GPU's region, that region has no volume support. Use a pod-local persistent disk instead — set it when creating the pod, mounted at /workspace. It survives image swaps and restarts but is deleted with the pod.

02

Deploy the pod on a shell image

Pods → Deploy. Attach the volume from step 01 first — that filters the GPU list to valid regions.

03

Open a terminal on the pod

Wait for status Running, then Connect → Start Web Terminal → Open Web Terminal. This needs no SSH key and is the simplest route.

For SSH instead, add your public key at Settings → SSH Keys before creating the pod, then use the direct command shown under Connect. See BUG-08 — the two SSH methods are not interchangeable.

04

Download the weights

In that terminal:

web terminal · pod
# --break-system-packages is required; see BUG-07
pip install --break-system-packages -U "huggingface_hub[cli,hf_xet]"

mkdir -p /workspace/models

hf download zai-org/GLM-5.3-Flash \
  --local-dir /workspace/models/GLM-5.3-Flash

Expect 306 GiB across 62 shards in roughly 7 minutes at ~750 MB/s. If your terminal disconnects, re-run the same command — it resumes.

Confirm before moving on:

verify download
ls /workspace/models/GLM-5.3-Flash/*.safetensors | wc -l   # 62
du -sh /workspace/models/GLM-5.3-Flash                     # 306G
ls /workspace/models/GLM-5.3-Flash/processor_config.json   # must exist
05

Swap the pod to vLLM

Back in the console, open the pod's ⋯ menu → Edit Pod. Change the image and set the start command. The pod keeps its ID, its volume and its GPUs.

container image
vllm/vllm-openai:glm53-flash-x86_64-cu130

Use the cu129 tag instead if your host reports CUDA 12.8 rather than 13.0 — the console shows this on the pod.

container start command · replace YOUR_SECRET_KEY
--model /workspace/models/GLM-5.3-Flash \
--served-model-name glm53 \
--tensor-parallel-size 4 \
--max-model-len 65536 \
--max-num-seqs 256 \
--gpu-memory-utilization 0.92 \
--api-key YOUR_SECRET_KEY \
--enable-auto-tool-choice \
--tool-call-parser glm47 \
--reasoning-parser glm45 \
--host 0.0.0.0 \
--port 8000

Every flag earns its place:

FlagWhy
--model /workspace/…A local path, never a repo ID — see BUG-01
--max-num-seqs 256Prevents a Mamba-cache crash — see BUG-02

06

Wait — and know what you're waiting for

Watch the container log. Startup has three phases and the last one dominates:

PhaseDurationLog signal
Engine init~1 minResolved architecture: Glm5Next…
Weight load~40 secModel loading took 75.65 GiB
Kernel JIT + CUDA graph capture13–18 min[Autotuner]: Autotuning process…

Distinguishing "loading" from "crash-looping" matters. Both show repeated shard-loading progress. The reliable tell is the worker PID in log lines like (Worker_TP0 pid=1048). A stable PID over several minutes means it is loading. A PID that changes every few minutes means it is crashing and restarting — stop waiting and read section 08.

05

Verify it works

Your endpoint is https://<POD_ID>-8000.proxy.runpod.net/v1, with the pod ID from the console. Run all three checks — the third is the one people skip.

local machine
POD="your-pod-id"
KEY="YOUR_SECRET_KEY"
BASE="https://$POD-8000.proxy.runpod.net/v1"

# 1 — is it serving?
curl "$BASE/models" -H "Authorization: Bearer $KEY"

# 2 — does it generate?
curl "$BASE/chat/completions" -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"glm53","messages":[{"role":"user","content":"Reply with exactly: it works"}],"max_tokens":64}'

# 3 — is a WRONG key rejected? Must print 401.
curl -o /dev/null -w '%{http_code}\n' "$BASE/models" -H "Authorization: Bearer wrong"

Reading the results

  • 200 plus a model named glm53 — serving correctly.
  • 502 — the proxy is up but vLLM is not listening. Still starting, or crash-looping.
  • 404 — the container is mid-restart.
  • Anything but 401 on check 3 — your endpoint is unauthenticated and publicly reachable. Fix before continuing.

A correct response also carries a populated reasoning field separate from content, confirming the reasoning parser is active.

06

The uncensored variant

Identical procedure, two changed strings. If the base is already running you do not need a new pod.

Check your free space first

Each build is 306 GiB. Both fit only on a volume of ~700 GB or more. On a 400–420 GB disk you must delete the base first — and re-downloading it later is another 7 minutes.

01

Return the pod to the shell image

Edit Pod → set the image back to runpod/pytorch:1.0.2-cu1281-torch280-ubuntu2404 and clear the start command. The vLLM image has no shell server, so you cannot get a terminal while it is running (BUG-08).

02

Download the abliterated weights

web terminal · pod
# only if you need the space:
# rm -rf /workspace/models/GLM-5.3-Flash

pip install --break-system-packages -U "huggingface_hub[cli,hf_xet]"

hf download dealignai/GLM-5.3-Flash-UNCENSORED-FP8 \
  --local-dir /workspace/models/GLM-5.3-UNCENSORED
03

Swap back to vLLM with the new path

Same image and same flags as step 05 earlier, with two lines changed:

changed lines only
--model /workspace/models/GLM-5.3-UNCENSORED \
--served-model-name glm53-uncensored \

Giving it a distinct served name keeps the two builds unambiguous in any client. Verify with section 05, substituting glm53-uncensored as the model.

Result

The abliterated build loaded and served on the first attempt — 75.65 GiB per worker, matching the base exactly — and passed chat, tool-calling and auth checks identically. Despite having no prior downloads on Hugging Face, it presented no checkpoint-specific problems.

07

Connect OpenCode

vLLM speaks the OpenAI API, so any OpenAI-compatible client works. OpenCode needs two files that reference each other by a shared ID — understanding that is the difference between this taking two minutes and taking an hour.

How the two files connect

Built-in providers ship with their URLs known. Yours does not exist in any registry, so you supply the address. The provider ID is only a lookup key joining a credential to a connection:

the join
          provider id: "runpod-glm"
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
   auth.json          opencode.jsonc
   your API key       baseURL + models
   (you type it)      (you write it)

Step 1 — write the config

Create opencode.jsonc in your global OpenCode config directory (~/.config/opencode/ on macOS, Linux and Windows alike). Use the global path rather than a project folder so it works from any directory.

~/.config/opencode/opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "runpod-glm": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "GLM-5.3-Flash (RunPod)",
      "options": {
        "baseURL": "https://YOUR_POD_ID-8000.proxy.runpod.net/v1"
      },
      "models": {
        "glm53": {
          "name": "GLM-5.3-Flash",
          "limit": { "context": 65536, "output": 16384 },
          "tool_call": true
        },
        "glm53-uncensored": {
          "name": "GLM-5.3-Flash UNCENSORED",
          "limit": { "context": 65536, "output": 16384 },
          "tool_call": true
        }
      }
    }
  }
}

Step 2 — register the credential

Launch opencode, run /connect, choose Other, and enter:

  • Provider ID: runpod-glm — must match the config exactly
  • API key: the secret from your start command

This writes ~/.local/share/opencode/auth.json. Note the different tree: config lives under .config, credentials under .local/share.

Step 3 — restart, then select

Quit OpenCode completely and relaunch. It does not reload config live. Then /models and pick your provider.

Three things that will bite you
  • The models list is not validated. It's a menu. One vLLM process serves one checkpoint, so an entry whose name isn't in your start command returns 404 — the config will offer it anyway.
  • A project-level opencode.json overrides the global one. Stray copies cause auth that works in one directory and fails in another.
  • The base URL contains the pod ID. Editing a pod keeps it; terminating and recreating does not. Rebuild the pod and you must update this file.
08

Bugs and gotchas

Encountered during a real deployment on 2026-08-27. The first two will hit you — they are unavoidable with this model on this engine, and the launch command on the model card triggers both.

BUG-01

A Hugging Face repo ID crashes on startup

Blocking
Symptom
FileNotFoundError: 'zai-org/GLM-5.3-Flash/processor_config.json' seconds after launch, before any weights load.
Cause
Glm5NextProcessor.from_pretrained calls open() on the model string as though it were a directory, instead of resolving it through the Hub. The file exists in the repo; it is simply never downloaded. Any repo ID fails.
Fix
Download the weights yourself and pass a local directory to --model. This is the entire reason the guide splits download and serve into two images.
BUG-02

Crash-loop during CUDA graph capture

Blocking
Symptom
ValueError: max_num_seqs (1024) exceeds available Mamba cache blocks (512). Weights load fully, then it dies and restarts — roughly every three minutes, indefinitely.
Cause
34 of 45 layers are KDA linear-attention, and every concurrent sequence needs its own state block. vLLM's default of 1024 sequences demands more blocks than the memory left after 306 GiB of weights can supply.
Fix
Add --max-num-seqs 256. Also raise --gpu-memory-utilization to 0.92 for headroom. Values above 512 sit on the boundary and are fragile.
BUG-03

The architecture is not in any vLLM release

Plan around
Symptom
Stock vLLM images do not recognise glm5_next.
Cause
Support is an unmerged pull request (vllm#53906). Only per-model preview images carry it.
Fix
Use vllm/vllm-openai:glm53-flash-x86_64-cu130 (or -cu129). Match the tag to your host CUDA version — a cu130 image needs a CUDA 13 driver.
BUG-04

Loading and crash-looping look identical

Wastes hours
Symptom
Shard-loading progress bars advance repeatedly and the endpoint stays on 502. It reads like slow progress.
Cause
Each crash restarts the whole load, reprinting the same progress from zero.
Fix
Compare worker PIDs across several minutes: (Worker_TP0 pid=1048). Stable PID means loading; changing PID means crashing. Total healthy startup is ~20 minutes — past 25, assume a crash and grep the log for Error or Traceback.
BUG-05

The model card's launch command does not work

Misleading
Symptom
Copying the published command produces out-of-memory or unsupported-flag errors.
Cause
It assumes a GB200. --tensor-parallel-size 4 needs 76.5 GiB per GPU, which OOMs on any 80 GB card, and --kv-cache-dtype fp8 is Blackwell-only for this model.
Fix
Use the command in section 04. TP4 requires ≥141 GB GPUs; on 80 GB cards use eight of them with TP8.
BUG-06

Storage and GPUs live in different datacenters

Plan around
Symptom
"There are no longer any instances available with the requested specifications", repeatedly, for a GPU the catalogue lists as available.
Cause
A network volume pins the pod to its datacenter. Availability is per-datacenter, not global. In testing the only region with free 4 × H200 offered no network volumes at all, and standard-tier storage was unavailable in the region that did.
Fix
Confirm both before creating the volume — volumes cannot move, and a fresh 306 GiB download is only ~7 minutes. Where regions do not overlap, use a pod-local persistent disk and accept losing it on teardown.
BUG-07

pip refuses to install

Trivial
Symptom
error: externally-managed-environment
Cause
PEP 668 protects the system Python in the base image.
Fix
Add --break-system-packages. Safe in a disposable container.
BUG-08

SSH works, then stops working

Confusing
Symptom
Permission denied (publickey) on the proxy address, or SSH vanishing entirely after switching to the vLLM image.
Cause
Two unrelated mechanisms. Proxy SSH (ssh.runpod.io) authenticates against account-level keys in Settings. Direct SSH uses the pod's PUBLIC_KEY variable — and only works on images that run a shell server. The vLLM image runs vllm serve as its entrypoint and has none.
Fix
Add your key at Settings → SSH Keys for the proxy method. Do all shell work while on the PyTorch image, or just use the web terminal.
BUG-09

The endpoint is public, and the key is logged

Security
Symptom
Anyone with the URL can use your GPUs. Separately, your key appears in plaintext in the container log.
Cause
The RunPod proxy URL is publicly routable and vLLM has no authentication by default. vLLM also prints its full argument list, including --api-key, at startup.
Fix
Always set --api-key, and verify a wrong key returns 401. Treat the key as visible to anyone who can read your pod logs, and rotate it if those are shared.
BUG-10

Prefill is slower than advertised

Cosmetic
Symptom
WARNING: No MLA prefill backend supports this model; sparse MLA will use the top-k MQA path only
Cause
No optimised dense-MHA prefill backend exists yet for this attention layout.
Fix
None needed — it serves correctly. Expect prefill throughput below the model card's figures until the architecture merges upstream.
BUG-11

A deprecated download variable does nothing

Trivial
Symptom
FutureWarning: HF_HUB_ENABLE_HF_TRANSFER is deprecated
Cause
Superseded by Xet-based transfer.
Fix
Use HF_XET_HIGH_PERFORMANCE=1. Harmless either way — downloads still reached ~750 MB/s.
BUG-13

Pod creation on REST v2 is broken upstream

Blocking
Symptom
Field "objectMounts" is not defined by type "PodFindAndDeployOnDemandInput" on every POST /v2/pods. Observed 2026-08-28; the identical payload worked on 2026-08-27.
Cause
RunPod's REST layer injects objectMounts: null into a GraphQL mutation whose schema rejects it. Both halves are RunPod's own. The field appears nowhere in their published v2 OpenAPI spec — an unreleased feature shipped ahead of the schema supporting it. GET /v2/gputypes returning 404 is the same churn.
Not you
It fails on a minimal {name, image, gpu} body, for every GPU type, every datacenter, via raw curl and via RunPod's own MCP client. Do not debug your payload — nothing in it is the cause.
Fix
Create pods through GraphQL instead — the same operation without the broken translation layer (see section 10). Read, PATCH and DELETE on REST v2 are unaffected, so use REST for everything else. Retest REST periodically and prefer it once fixed.
BUG-12

Restarting is 25× slower than the first start

Budget for it
Symptom
The first launch loads all 62 shards in ~37 seconds. A later restart of the same pod, same weights, takes 13.5 minutes — about 13 s/shard instead of 0.5 s/shard.
Cause
The first load reads from the host page cache, because the files were written moments earlier by the download. Any later start is a cold read of 306 GiB from network-backed storage. Same data, different path.
Fix
None — it is the honest cost of a restart. Plan for ~25 minutes and ~$7 per restart on 4 × H200, not the 20 minutes the first boot suggests. Change several flags at once rather than iterating one at a time. The kernel-JIT cache does not help either: it lives on the container disk, which is wiped on every restart.
09

Raising the context limit

The guide starts you at 65,536 tokens because a conservative first boot is easier to debug. The model itself declares 1,048,576 — and on 4 × H200 you can actually reach it. This model is unusually cheap on KV cache, so context is rarely the binding constraint.

Why it's so cheap

Two architectural properties cut KV memory by roughly an order of magnitude versus a conventional dense transformer:

  • Only 11 of 45 layers cache anything. The other 34 are KDA linear-attention with fixed-size state per sequence — their cost does not grow with context.
  • NoPE MLA compresses KV to a 512-dimension latent. With qk_rope_head_dim: 0 there is no separate rotary cache to store.
per-token KV cost
11 layers × 512 latent dims × 2 bytes (BF16)  =  11,264 bytes
                                              ≈  11 KiB per token

What that buys you

On 4 × H200 at --gpu-memory-utilization 0.92: 483 GiB usable, minus 306 GiB of weights and ~25 GiB of activations and CUDA graphs, leaves roughly 152 GiB of KV pool ≈ 14.5M tokens.

max-model-lenKV per sequenceConcurrent full-length sequences
65,5360.69 GiB~221
131,0721.38 GiB~111
262,1442.75 GiB~55
524,2885.50 GiB~28
1,048,57611.00 GiB~14
Corroboration

This calculation gives a 14.5M-token pool. The published vLLM recipe independently reports a 14.92M-token KV pool at TP4 for this model — close enough to trust the arithmetic. A running server at 65K context with three concurrent requests showed KV usage of 0.3–1.9%, consistent with a pool this large.

How to change it

Edit one flag and restart. There is no way to change context on a live server — the KV pool is allocated at startup.

  1. Pods → ⋯ → Edit Pod
  2. Change --max-model-len in the start command
  3. Save. The container restarts and reloads the model.

Budget ~25 minutes and roughly $7 per attempt on 4 × H200. Weights are already on disk, so this is a reload rather than a re-download — but see BUG-12: a reload is far slower than the first load, and most of that 25 minutes is unavoidable. Batch your flag changes rather than testing one at a time.

maximum context on 4 × H200
--max-model-len 1048576 \
--max-num-seqs 256 \
--gpu-memory-utilization 0.92

If it refuses to start

vLLM fails fast when the pool cannot hold one full-length sequence:

startup error
ValueError: The model's max seq len (1048576) is larger than the maximum
number of tokens that can be stored in KV cache. Try increasing
`gpu_memory_utilization` or decreasing `max_model_len`.

Recent vLLM builds append a usable hint — "the estimated maximum model length is 220480". Take that number and round down. Otherwise, in order of preference:

  • Raise --gpu-memory-utilization toward 0.95. Above that, CUDA graph capture starts failing.
  • Lower --max-num-seqs. Fewer concurrent sequences frees Mamba state blocks — but keep BUG-02 in mind: too high crashes, and the ceiling moves with available memory.
  • Add GPUs. Going TP8 roughly doubles the pool.
  • On Blackwell only, add --kv-cache-dtype fp8 to halve KV cost. Unsupported on Hopper for this model.
Memory is not the limit — prefill time is

A million-token prompt still has to be processed. With chunked prefill at the default 8,192 tokens per batch that is roughly 128 sequential chunks, and per BUG-10 this model currently runs a top-k MQA prefill path rather than an optimised dense one. Expect a first-token latency measured in minutes at extreme context. Raising --max-num-batched-tokens to 16,384 helps, at the cost of activation memory.

Tell your client about it

Raising the server limit is only half the job — clients advertise their own. In OpenCode, update the model's limit.context to match, or it will keep truncating at the old value:

opencode.jsonc
"limit": { "context": 1048576, "output": 16384 }

A note on quality

A declared window is not a guarantee of comprehension across it. 1,048,576 is what the architecture supports and what the server will accept; how well the model actually reasons over a million tokens is a separate question this guide does not answer. If retrieval accuracy matters, test at your intended length rather than assuming the maximum works well.

10

Doing it from the CLI

Every console step above has a REST equivalent. This section is the more trustworthy of the two: these are the exact calls used to build the deployment this guide documents, whereas the console instructions were written from RunPod's published UI rather than performed click by click.

Setup

Create a key at console.runpod.io → Settings → API Keys with Read/Write permission. Read-only cannot create pods.

environment
export RUNPOD_API_KEY="rpa_..."
export API="https://api.runpod.io/v2"
export AUTH="Authorization: Bearer $RUNPOD_API_KEY"
Use v2, not v1

https://rest.runpod.io/v1 is deprecated and takes a different request schema. Posting a v2 body to it returns Extra input keys provided in request body naming image, gpu, disk and mounts — confusing, because those keys are all valid on v2.

Check capacity before you commit

Availability is per-datacenter and changes by the minute. A GPU listed as available globally may be unobtainable in the region your storage lives in.

discover GPU types and datacenters
curl -s "$API/gputypes" -H "$AUTH" | python -m json.tool
curl -s "$API/datacenters" -H "$AUTH" | python -m json.tool

Create the pod

Write the body to a file — it is long, and you will edit and resend it several times.

create-pod.json
{
  "name": "glm53-flash",
  "image": "runpod/pytorch:1.0.2-cu1281-torch280-ubuntu2404",
  "cloud": "SECURE",
  "dataCenterIds": ["US-GA-2"],
  "gpu": { "id": "NVIDIA H200", "count": 4, "allowedCudaVersions": ["13.0"] },
  "disk": 60,
  "startSsh": true,
  "ports": ["8000/http", "22/tcp"],
  "env": {
    "PUBLIC_KEY": "ssh-ed25519 AAAA... you@host",
    "HF_XET_HIGH_PERFORMANCE": "1"
  },
  "mounts": { "persistent": { "size": 420, "path": "/workspace" } }
}
send it
curl -sS -X POST "$API/pods" -H "$AUTH" \
  -H 'Content-Type: application/json' -d @create-pod.json
If that returns an objectMounts error — use GraphQL

As of 2026-08-28 POST /v2/pods fails upstream (BUG-13). Do not debug your request; a four-field body fails identically. Create the pod through GraphQL instead — the same operation, one layer below the fault:

GraphQL pod creation — the working bypass
python -c "
import json,sys,pathlib,os
pub=pathlib.Path(os.path.expanduser('~/.ssh/id_ed25519.pub')).read_text().strip()

Use GraphQL variables, never string interpolation — an SSH key containing a backslash (azuread\user) produces Invalid character escape sequence in an inline literal.

Field names differ from REST: volumeInGb / volumeMountPath replace mounts.persistent, ports is a comma-separated string, env is a list of {key, value} pairs, and there is no dataCenterIds — GraphQL simply picks a region with capacity.

A SUPPLY_CONSTRAINT error here is genuine capacity exhaustion and worth retrying. An objectMounts error is a schema fault and never is. Do not confuse them.

Two mount forms, and the choice is permanent:

  • "mounts": {"persistent": {"size": 420, "path": "/workspace"}} — pod-local disk. Works in any datacenter. Deleted with the pod.
  • "mounts": {"network": [{"volumeId": "abc123", "path": "/workspace"}]} — a network volume. Survives the pod, but pins it to that volume's datacenter and only exists in regions that support them.

Mount kind is immutable after creation. A PATCH adding a network mount to a pod that had none is rejected. Decide before you POST.

Expect There are no longer any instances available with the requested specifications when capacity is tight. That is a scheduling failure, not a malformed request — retry, or widen dataCenterIds.

Swap to vLLM without losing the pod

This is the key move. PATCH changes the image and start command in place — the pod keeps its ID, its GPUs, its storage and its URL. You never release the multi-GPU allocation, which matters when capacity is scarce.

patch image + args
curl -sS -X PATCH "$API/pods/$POD" -H "$AUTH" \
  -H 'Content-Type: application/json' -d '{
  "image": "vllm/vllm-openai:glm53-flash-x86_64-cu130",
  "args": "--model /workspace/models/GLM-5.3-Flash --served-model-name glm53 --tensor-parallel-size 4 --max-model-len 1048576 --max-num-seqs 256 --gpu-memory-utilization 0.92 --api-key YOUR_SECRET --enable-auto-tool-choice --tool-call-parser glm47 --reasoning-parser glm45 --host 0.0.0.0 --port 8000"
}'

The same call changes context length later — send only args, leaving image out. Any PATCH to either field restarts the container, so per BUG-12 that is ~25 minutes each time. Batch your changes.

Note the direction of travel: to get a shell back you must PATCH the image back to the PyTorch one, because the vLLM image runs no shell server (BUG-08).

Billing runs from pod start to termination, regardless of whether the model is loaded, idle or crash-looping. All prices are RunPod secure cloud, observed 2026-08-27.

Reducing the bill

  • Download on one GPU, serve on four. Creating a single-GPU pod for the download costs about $0.55 instead of $2.20 — but you then have to win the multi-GPU allocation again afterwards. When capacity is tight, holding the four-GPU pod through the download is the safer trade.
  • Stop, don't terminate. A stopped pod keeps its disk and its ID — so your OpenCode base URL stays valid — at a much lower rate.
  • Terminate properly when finished. Deleting a pod does not delete a network volume; that keeps billing until you delete it under Storage.

Teardown checklist

  1. Terminate the pod (Pods → ⋯ → Terminate).
  2. Delete the network volume (Storage → ⋯ → Delete) — this is the step most often missed.
  3. Confirm zero active resources on the billing page.
  4. Optionally remove the runpod-glm entry from auth.json.
The expensive mistake

A pod that crash-loops bills exactly like a healthy one. During testing, a stuck pod ran for fourteen minutes, restarting every three, before the pattern was spotted — about $4.30 for nothing. Check worker PIDs early (BUG-04) rather than assuming a long startup.

Procedure verified end to end on 2026-08-27: 4 × H200 SXM, RunPod secure cloud, vLLM 0.1.dev20051+g487ecf187, FlashInfer 0.6.17, CUDA 13.0. Both the base and abliterated builds reached a serving state and passed chat, tool-calling and authentication checks.

Version numbers and flags are tied to a pre-release build. Once glm5_next merges into vLLM proper, the preview image will be unnecessary and BUG-01 and BUG-02 may be fixed upstream — check current documentation before assuming these workarounds are still required.
