Companion guide · LiteLLM bridge

Claude Code on GLM

Point Claude Code at your own self-hosted GLM-5.3-Flash endpoint. Claude Code speaks only the Anthropic API and vLLM speaks only OpenAI, so a translator sits between them. This is how to build it.

LiteLLM 1.98+ Windows / PowerShell Companion to the deployment guide
01

Why a proxy is needed

Claude Code cannot talk to your endpoint directly. It sends requests in Anthropic Messages API format to whatever ANTHROPIC_BASE_URL points at. vLLM serves the OpenAI Chat Completions format. Different request shapes, different response shapes, different tool-calling conventions.

LiteLLM sits in the middle: it accepts Anthropic-format requests on /v1/messages and re-emits them as OpenAI calls to your pod, translating the responses back.

  Claude Code                LiteLLM :4000              RunPod vLLM
  ───────────                ─────────────              ───────────
  Anthropic format    ──▶    translates          ──▶    OpenAI format
  /v1/messages               both directions            /v1/chat/completions
                                                        glm53-uncensored
Set expectations

Claude Code's prompts, tool-use patterns and long-horizon behaviour are tuned for Claude specifically. GLM-5.3-Flash has working tool calls, so this functions — but agentic reliability may be rougher than a client with no such assumptions, like OpenCode. Treat it as an experiment rather than a drop-in replacement.

02

Before you start

  • A running GLM endpoint — see the deployment guide. You need its pod ID and API key.
  • Python 3.10+ and Claude Code installed.
  • Two terminal windows. The proxy runs in the foreground.
Check the version before installing

LiteLLM PyPI releases 1.82.7 and 1.82.8 were compromised with credential-stealing malware. Never install those. Verify what you are about to get:

check the version first
curl -s https://pypi.org/pypi/litellm/json | python -c "
import sys,json; v=json.load(sys.stdin)['info']['version']
print(v, '← DO NOT INSTALL' if v in {'1.82.7','1.82.8'} else 'ok')"

This matters more than usual here: the proxy is handed your endpoint key and sits on a machine holding your RunPod credentials.

03

Install

Use an isolated virtual environment. LiteLLM pulls a large dependency tree and should not be installed into system Python.

powershell · repo root
python -m venv .venv-litellm
.\.venv-litellm\Scripts\python.exe -m pip install --upgrade pip
.\.venv-litellm\Scripts\python.exe -m pip install "litellm[proxy]"

# confirm what landed
.\.venv-litellm\Scripts\python.exe -c "import litellm; print(litellm.__version__)"

Add .venv-litellm/ to .gitignore.

Wait for it to finish

This pulls a large dependency tree and takes several minutes. The venv directory appears almost immediately, long before the entry point does — starting the proxy early gives you litellm.exe is not recognized, which looks like a broken install but is only impatience. Confirm the binary exists first:

confirm before starting the proxy
ls .\.venv-litellm\Scripts\litellm.exe
Two Windows traps, both fatal at startup

1. Console encoding. LiteLLM prints a Unicode banner; the default cp1252 codec cannot encode it and the proxy exits with UnicodeEncodeError. Set PYTHONUTF8=1 and PYTHONIOENCODING=utf-8 before launching.

2. Non-ASCII in config.yaml. An em-dash or smart quote in a comment — easily introduced by pasting — is saved as cp1252 and read back as UTF-8, giving UnicodeDecodeError: invalid start byte. Keep config.yaml pure ASCII.

04

Configure the proxy

litellm/config.yaml maps friendly model names onto your endpoint.

litellm/config.yaml
model_list:
  # main model — Claude Code's primary
  - model_name: glm53
    litellm_params:
      model: openai/glm53-uncensored
      api_key: os.environ/GLM_API_KEY
      api_base: https://YOUR_POD_ID-8000.proxy.runpod.net/v1
    model_info:
      # must match vLLM --max-model-len, else clients truncate early
      max_input_tokens: 1048576
      max_output_tokens: 16384
      max_tokens: 1048576

  # Claude Code also calls a small/fast model for titles and summaries
  - model_name: glm53-small
    litellm_params:
      model: openai/glm53-uncensored
      api_key: os.environ/GLM_API_KEY
      api_base: https://YOUR_POD_ID-8000.proxy.runpod.net/v1
    model_info:
      max_input_tokens: 1048576
      max_output_tokens: 16384
      max_tokens: 1048576

litellm_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  drop_params: true
Without model_info you silently lose the context window

LiteLLM does not discover your model's limits from the backend. Omit model_info and /model/info reports max_input_tokens: None — so Claude Code has no idea it can use a million tokens and falls back to conservative defaults.

Nothing errors. You simply never get the window you are paying four H200s to provide.

confirm the limits actually registered
curl -s "http://127.0.0.1:4000/model/info" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" | python -c "
import sys,json
for m in json.load(sys.stdin)['data']:
    i = m.get('model_info') or {}
    print(m['model_name'], i.get('max_input_tokens'), i.get('max_output_tokens'))"

# expect: glm53 1048576 16384   -- 'None' means model_info was not applied

Three places must agree on the context length, and nothing checks them against each other:

  1. vLLM's --max-model-len — the only real limit, enforced server-side
  2. LiteLLM's model_info.max_input_tokens — what the proxy advertises
  3. The client's own setting, if it has one (OpenCode's limit.context)

Set lower than the server and you waste the window silently. Set higher and requests fail mid-conversation once context accumulates, which reads as intermittent and is miserable to diagnose.

Why each part is there

SettingWhy
openai/<name>The openai/ prefix tells LiteLLM to speak OpenAI to the backend. The part after it is the --served-model-name from your vLLM command
glm53-smallNot optional. Claude Code calls a separate small model for titles and summaries. If it is unmapped, background tasks error in ways that look like total failure. One backend, two names
master_keyThe token Claude Code presents to the proxy. Distinct from your endpoint key — invent one, e.g. sk-local-<random>
drop_params: trueSilently discards parameters the backend does not support instead of erroring. Anthropic and OpenAI do not have identical parameter sets
os.environ/…Reads from the environment so real keys stay out of the config file
05

Environment variables

Claude Code needs four. What each does:

VariableValuePurpose
ANTHROPIC_BASE_URLhttp://127.0.0.1:4000Sends requests to the proxy instead of Anthropic
ANTHROPIC_AUTH_TOKEN$LITELLM_MASTER_KEYAuthenticates to the proxy
ANTHROPIC_MODELglm53The main model name from config.yaml
ANTHROPIC_SMALL_FAST_MODELglm53-smallBackground tasks. Omit it and those fail
Critical: Claude Code ignores LiteLLM's context window

Setting model_info.max_input_tokens in LiteLLM is not enough. Claude Code resolves the context window from its own internal model list and never queries the proxy. For a model it does not recognise, it assumes a small window and auto-compacts aggressively to stay inside it.

The symptom is not an error. Sessions simply run out of context far sooner than they should, as if the million-token window did not exist. Claude Code says so itself:

"glm53" is not a model this version of Claude Code recognizes, so auto-compact will keep this session within [N] tokens (the context window it assumes). Map it in the modelOverrides setting or update Claude Code.

Two extra variables fix it:

required for any non-Claude model
$env:CLAUDE_CODE_MAX_CONTEXT_TOKENS = "1048576"
$env:CLAUDE_CODE_MAX_OUTPUT_TOKENS  = "16384"

Related variables in the same build, worth knowing:

  • CLAUDE_CODE_AUTO_COMPACT_WINDOW — the threshold at which compaction triggers
  • CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1 — stops it enforcing an assumed window for unrecognised models entirely
  • A modelOverrides setting also exists, taking contextWindow and maxOutputTokens per model. It lives in settings and therefore applies globally — the env vars are safer because they stay scoped to the launcher

Verify these exist in your build rather than trusting any guide, since they change between versions:

confirm the override exists in your binary
grep -aoE "CLAUDE_CODE_MAX_[A-Z_]+" \
  ~/.local/share/claude/versions/<VERSION> | sort -u
Never set these globally

Set them at process scope only. A User- or Machine-scope ANTHROPIC_BASE_URL silently redirects every Claude Code session to your GLM endpoint — including your normal work. When the pod is down or torn down, Claude Code fails with connection errors and no obvious cause.

Use a launcher script so claude stays normal and a separate command gets GLM. Two commands, no ambiguity.

06

The two scripts

Both load .env into the current process only.

Write these files as pure ASCII too

PowerShell reads a .ps1 without a byte-order mark as cp1252, not UTF-8. A single em-dash or smart quote — trivially introduced by pasting from a document or an AI response — arrives as three garbage characters, and if it lands inside or near a quoted string the parser dies with a misleading error:

The string is missing the terminator: " followed by Missing closing '}' in statement block, pointing at a line that looks perfectly fine.

The reported line is where the parser gave up, not where the bad byte is. Do not debug that line. Find the actual character:

locate non-ASCII bytes in a script
python -c "
import pathlib
raw = pathlib.Path('litellm/claude-glm.ps1').read_bytes()
print([(i, hex(b)) for i, b in enumerate(raw) if b > 127])"

# e2 80 94 = em-dash    e2 80 99 = smart apostrophe
# e2 80 9c / 9d = smart quotes

Either replace them with ASCII equivalents, or save the file as UTF-8 with BOM, which is what makes PowerShell read it as UTF-8. ASCII is the simpler guarantee.

Verify a script parses without running it:

parse check
$errs = $null
[void][System.Management.Automation.Language.Parser]::ParseFile(
  "$PWD\litellm\claude-glm.ps1", [ref]$null, [ref]$errs)
if ($errs.Count) { $errs | ForEach-Object { $_.Extent.StartLineNumber, $_.Message } }
else { "parses OK" }

Start the proxy

litellm/start-proxy.ps1
$ErrorActionPreference = "Stop"
$root = Split-Path -Parent $PSScriptRoot

Get-Content "$root\.env" | ForEach-Object {
  if ($_ -match '^\s*([A-Za-z_][A-Za-z0-9_]*)\s*=\s*(.*)$') {
    [Environment]::SetEnvironmentVariable($Matches[1], $Matches[2].Trim(), "Process")
  }
}

if (-not $env:GLM_API_KEY)        { throw "GLM_API_KEY missing from .env" }
if (-not $env:LITELLM_MASTER_KEY) { throw "LITELLM_MASTER_KEY missing from .env" }

Write-Host "LiteLLM proxy -> http://127.0.0.1:4000" -ForegroundColor Green
& "$root\.venv-litellm\Scripts\litellm.exe" --config "$root\litellm\config.yaml" --port 4000

Launch Claude Code against it

litellm/claude-glm.ps1
$ErrorActionPreference = "Stop"
$root = Split-Path -Parent $PSScriptRoot

Get-Content "$root\.env" | ForEach-Object {
  if ($_ -match '^\s*([A-Za-z_][A-Za-z0-9_]*)\s*=\s*(.*)$') {
    [Environment]::SetEnvironmentVariable($Matches[1], $Matches[2].Trim(), "Process")
  }
}

# fail clearly if the proxy is not up, rather than inside Claude Code
try { $null = Invoke-WebRequest "http://127.0.0.1:4000/health/liveliness" -TimeoutSec 5 -UseBasicParsing }
catch { Write-Host "Proxy not reachable — run start-proxy.ps1 first." -ForegroundColor Red; exit 1 }

$env:ANTHROPIC_BASE_URL         = "http://127.0.0.1:4000"
$env:ANTHROPIC_AUTH_TOKEN       = $env:LITELLM_MASTER_KEY
$env:ANTHROPIC_MODEL            = "glm53"
$env:ANTHROPIC_SMALL_FAST_MODEL = "glm53-small"

claude @args

Run it

two terminals

.\litellm\start-proxy.ps1

Verify the chain before trusting it

Test each hop separately, so a failure tells you where it broke.

hop 1 — is the pod serving?
curl -s "https://YOUR_POD_ID-8000.proxy.runpod.net/v1/models" \
  -H "Authorization: Bearer $GLM_API_KEY"
hop 2 — is the proxy translating?
curl -s "http://127.0.0.1:4000/v1/messages" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H 'content-type: application/json' \
  -H 'anthropic-version: 2023-06-01' \
  -d '{"model":"glm53","max_tokens":64,
       "messages":[{"role":"user","content":"Reply with exactly: it works"}]}'

Hop 2 is the real test: an Anthropic-shaped request returning an Anthropic-shaped response proves the translation works. If hop 1 passes and hop 2 fails, the fault is in the proxy or config — not your pod.

08

When it breaks

SymptomCause and fix
Connection refused on :4000 Proxy not running, or it crashed on startup. Check terminal 1 — a missing env var throws immediately
Proxy says it started, but :4000 refuses connections It bound to a different port. If 4000 is already taken, LiteLLM silently falls back to a random free port instead of erroring. Check the startup line: Uvicorn running on http://127.0.0.1:NNNN. Usually means a previous instance is still alive
Config changes have no effect A stale proxy is still holding the port and serving the old config. On Windows pkill does not reliably kill it. Use Get-Process -Name litellm | Stop-Process -Force, confirm none remain, then start one instance. Stacked proxies are easy to create and hard to notice
max_input_tokens: None in /model/info The model_info block is missing or was not picked up — often because you edited config.yaml while a stale proxy held the port. Claude Code then works but silently uses a small context window
401 from the proxy ANTHROPIC_AUTH_TOKEN does not match LITELLM_MASTER_KEY. These are the proxy's credentials, not your endpoint key
502 / connection error from the proxy The proxy is up but the pod is not. Test hop 1. A pod takes ~25 min to serve after a restart
model not found ANTHROPIC_MODEL must match a model_name in config.yaml, and the part after openai/ must match vLLM's --served-model-name. Three names, all must agree
Chat works, titles or summaries fail ANTHROPIC_SMALL_FAST_MODEL is unset or unmapped. Add glm53-small to config.yaml
Errors mentioning an unexpected parameter Set drop_params: true. Anthropic sends fields OpenAI backends reject
Your normal Claude Code broke You set ANTHROPIC_BASE_URL at User scope. Clear it: [Environment]::SetEnvironmentVariable("ANTHROPIC_BASE_URL",$null,"User"), then open a new terminal
Tool calls ignored or malformed Check vLLM was started with --enable-auto-tool-choice --tool-call-parser glm47. That is server-side; no proxy setting fixes it
litellm.exe is not recognized The install has not finished. pip install "litellm[proxy]" pulls a large dependency tree and takes several minutes — the venv exists long before the entry point does. Confirm with ls .venv-litellm\Scripts\litellm.exe before starting the proxy
UnicodeEncodeError: 'charmap' codec can't encode on startup Windows-specific. LiteLLM prints a Unicode startup banner that the default cp1252 console encoding cannot render, and the proxy exits. Set $env:PYTHONUTF8 = "1" and $env:PYTHONIOENCODING = "utf-8" before launching — the supplied start-proxy.ps1 does this
The string is missing the terminator: " plus Missing closing '}' A non-ASCII character in the .ps1 file. PowerShell reads scripts without a BOM as cp1252, so a UTF-8 em-dash or smart quote becomes three bad bytes. The reported line is not where the problem is — it is where the parser gave up. Scan for bytes > 127 (section 06) rather than reading the line it names
UnicodeDecodeError: 'utf-8' codec can't decode byte 0x97 Your config.yaml contains a non-ASCII character — typically a smart quote or em-dash pasted into a comment, saved as cp1252. Write config.yaml as pure ASCII. Check with: python -c "print([hex(b) for b in open('litellm/config.yaml','rb').read() if b>127])"
09

Worth knowing

The pod ID is baked into config.yaml

Your endpoint URL contains the pod ID, so every redeploy needs config.yaml updated. Editing a pod keeps its ID; terminating and recreating does not.

This is also the argument for the proxy beyond Claude Code: with several clients pointed at LiteLLM instead of the pod, only one file changes after a redeploy.

The proxy is a second place your key lives

GLM_API_KEY is now in .env, in the vLLM start command, in the pod's logs, and passed to LiteLLM. Bear that in mind when deciding whether to rotate it.

Two hops of latency

Every request now crosses your machine, then the public internet to RunPod. The proxy adds little on its own, but it is another process that can stall or die independently of both ends.

Is it worth it?

You get a familiar interface on your own model. You pay with a proxy to keep running, a config file to maintain, and an agent loop tuned for a different model. If the appeal is only "use my own model from a terminal", a client that speaks OpenAI natively — OpenCode, Crush, goose, Aider — costs less to operate.
